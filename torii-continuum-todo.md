- **CONT-COMPLETE-1 — the sign-in the agent accepted and the app then threw away. DONE v0.2.97-alpha (frontend + docs + integration tests; NOT deployed from the subagent — parent hands the operator the deploy block).** **Why.** v0.2.96 got a verifiable signature to the agent; production then showed the *next* failure. `auth.verify.success` was logged (200) and the operator still could not get in: the screen held **"Verifying your signature… step 3 of 3"**, and on the surfaces that re-render it returned to a login card with an **empty** status line. The cause was that a 200 was treated as a session. `verifyChallenge` stores a token only when `r.data.token` is present, but the caller branched on `verified.ok` alone — so a 200 that carried no usable token ran the entire success path: wrote the session marker, said "Signed in.", dispatched `continuum:session-changed`. The router then asked the guard, the guard said nobody is signed in, and the operator was *replaced* back onto the login card — whose re-render rebuilt the status element empty, destroying the only surface a message could have appeared on. Four real ways a 200 yields no session were indistinguishable: a proxy stripping or rewriting the body; a body that is not JSON; a token under a shape the client does not read; and a token already expired because the agent's clock and the operator's disagree. A fifth is not the agent's fault at all — private browsing or blocked site data means the token cannot be persisted. Worse, the born-expired case reached `startSessionRefresh()`, classified as EXPIRED and called `endSession()`, firing a **sign-out from inside the sign-in** that cleared the token and re-rendered the view out from under the message about to be written to it. **What.** (1) `describeCompletionFailure` (new, pure, in `src/login-stages.js`) classifies the post-200 state as `no_session` · `session_not_stored` · `session_expired`, or null when a session really landed. It deliberately does **not** re-derive liveness: it calls `classify` from the session state machine, the same function the router's guard and the renewal clock consume, because a second opinion about what "live" means is precisely the divergence that caused this. (2) Each kind names a **different** component — the agent/proxy, the browser's site-data setting, a clock — since one generic message would send an operator whose real fault is a blocked cookie jar off to debug a healthy VPS, the same wrong turn CONT-SIGNER-1 removed a layer earlier. All three are retryable, because each names something fixable. (3) `startLogin` confirms the session before claiming it, so the refresh loop is only ever handed a live one and the mid-sign-in sign-out is gone. (4) Success is announced **before** the side effects: both `startSessionRefresh()` and the `session-changed` dispatch re-render, and `navigate()` re-resolves even when the hash is unchanged, so a 'done' written afterwards landed on a detached node. The order is asserted (`['done', 'session-changed']`). **Tests.** 9 pure + 11 JSDOM integration driving the real login view and real router; the three kinds joined the exhaustive `KINDS` list so the pre-existing "every failure names a way forward" property covers them. Reverting `src/auth.js` alone fails 8 of 11 — the 3 that pass are the happy-path cases, the correct signal. Frontend **1731 pass / 60 files**; agent **423 pass**; alignment + release check **12 pass**; build clean.

- **CONT-SIGNER-1 — the login that only worked with one brand of signer. DONE v0.2.96-alpha (frontend + agent + docs + integration tests; NOT deployed from the subagent — parent hands the operator the deploy block).** **Why.** NIP-07 pins the call, not the answer. `signEvent(event)` is specified to return a signed event; nothing says what the returned object must *contain*, and the ecosystem disagrees. Some extensions echo the whole event back with `id`, `sig` and `pubkey` added — the one shape the flow was written against. Several NIP-46 bridges and remote signers return only `{ id, sig }`, because the bridge signs a payload it does not consider itself the owner of and hands back just the proof. Some omit `pubkey` and echo the rest. Some legitimately rewrite `created_at` (clock skew, batching), which NIP-07 permits and the agent accepts because the signature covers whatever the signer chose. The flow forwarded the signer's answer to `/api/auth/verify` **verbatim**, so two of those four shapes put a kind-less, tag-less object on the wire; the agent recomputed the id hash over it and refused; and the operator was told **"Your agent rejected the signature: id mismatch."** — the wrong component named, pointing a working setup at a healthy VPS. Three more failures sat alongside it: a signer that dropped the challenge tag was reported as the *agent's* "missing challenge tag" with a Retry against a signer that will do it again; a late-injecting extension was declared absent by a single synchronous read of `window.nostr`, and `no_signer` offers no retry, so an operator who *has* a signer hit a dead end; and a key that is not the owner was offered `recovery: 'retry'`, an invitation to press a button forever. **What.** (1) `src/signer-compat.js` (new, pure — no DOM, no network, no timers) reconciles the signer's answer against the event we asked it to sign, filling only the gaps and **preferring the signer everywhere it expressed an opinion**. That direction is load-bearing: the agent independently recomputes the id hash over `[0, pubkey, created_at, kind, tags, content]` and verifies `sig` against it, so reconciliation can produce a correctly-shaped payload but can never manufacture an acceptance — and preferring our own values would break the signer that rewrote `created_at`, a case that already worked. (2) The one hole nothing local can fill is `pubkey`; it is closed from NIP-07 `getPublicKey()`, the only correct source, since a key we chose would change the hash. A signer that will not name one fails honestly (`switch-signer`) rather than having a key invented for it. (3) A signer that dropped or rewrote the challenge tag is caught **before** the round trip and named as a signer fault, because re-adding the tag would only invalidate the id. (4) `window.nostr` is polled for 1.5s before concluding there is no signer, with the already-present case still paying nothing — not a tick. (5) `/api/auth/verify` refusals now carry a stable `code` (`malformed_event` · `wrong_kind` · `not_owner` · `challenge_expired` · `bad_signature` · `claim_failed`) beside the prose, and the browser routes on it instead of on English sentences: `not_owner` gets `switch-signer` and no retry, `challenge_expired` keeps its retry. An agent that sends no code degrades to exactly today's generic behaviour. (6) The install/switch copy became a frozen registry of NIP-07 signers instead of one vendor hard-coded in three places, which told an operator running a different signer that their setup was unsupported. (7) The same verbatim-forwarding defect on the memory-activation signer path is fixed with the same module. **Tests.** `src/signer-compat.test.js` (27, pins the reconciliation *direction*, not just the outcome), `src/signer-compat-integration.test.js` (25 — its `/api/auth/verify` stub applies the agent's real gates in the agent's real order, so a pass means the payload would actually be accepted, not merely that nothing threw), `agent/test/auth-verify-codes.test.js` (11, pins codes not prose, including that *no* refusal path returns `ok:false` with nothing to route on), plus additions to the login-stages, memory-activation and login-recovery suites. Stashing the source changes fails 20 of them.

- **CONT-SESSION-1 — the public login screen that refreshed into the Dashboard. DONE v0.2.95-alpha (frontend + docs + integration tests; NOT deployed from the subagent — parent hands the operator the deploy block).** **Why.** The operator was looking at the public login modal, had *not* signed in, pressed F5, and landed on the Dashboard. That can only happen if the screen and storage disagree, because on reload there is no screen to consult and storage wins. Reproducing it in JSDOM before touching anything found one defect wearing two costumes: **two auth writers persisted a token unconditionally the moment their network reply arrived, with no check that the intent which began the request was still current.** Cancel a login while `/api/auth/verify` is on the wire and the reply still stores the session — status line reads "Sign-in cancelled." while `isSessionLive()` is `true`. Sign out while the background renewal is on the wire and the reply rewrites a live token behind the login screen, then re-arms the renewal loop for the life of the tab. Verbatim, before the fix: `CANCELLED: true in flight: false` / `AFTER LATE VERIFY live: true` and `AFTER SIGNOUT live: false` / `AFTER RENEWAL LANDS live: true, sessionState: active`. **The reason CONT-LOGIN-1's generation guard did not catch this** is structural and worth remembering: that guard lives in `src/auth.js`, which is *above* the write in `src/data/agent.js`, so it could retire its own continuations but never the store. **What shipped.** An **auth epoch** in the module that owns the storage: every auth write is stamped with the epoch current when its request *started*, sign-out and any abandoned attempt bump it, and a reply from a superseded epoch is reported (`code: 'superseded'`) rather than persisted. `endAttempt()` bumps it, so cancel/timeout/failure all invalidate in flight writes; the narrow window between the token landing and the abandonment check is closed by clearing the exact token that attempt produced, matched by identity so a replacement attempt that already succeeded is never clobbered. The renewal loop now **stops** on a superseded reply instead of backing off and retrying behind the login screen. And root now boots from `rehydrateSession()` — the same authority `guarded()` uses — because rendering the public login screen from a weaker read than the guards use is the other half of how screen and storage came to disagree; it also drops a marker left by an expired token, so login never renders beside a stale "signed in as" artifact. Local-first projects (`continuum.v1`) survive sign-out, as before and now under test. 19 new integration tests, each performing a **real** hard refresh: the window is destroyed, the module registry reset, and a new app booted against the same localStorage.

- **CONT-LOGIN-1 — the stalled Nostr login: unbounded stages, a dead button, and no way out. DONE v0.2.94-alpha (frontend + docs + integration tests; NOT deployed from the subagent — parent hands the operator the deploy block).** **Why.** Sign-in could sit forever with nothing to press. Reproducing it in JSDOM before touching anything showed three separate causes wearing one costume. First, **only one of the three stages was bounded.** The signer had a 90s deadline; the challenge and verify requests silently inherited the generic 30s client budget — a budget sized for a model generating chat tokens, not for an agent answering a click someone is waiting on. Second, **there was no way out.** `cancelLogin` did not exist, so a signer popup that never appeared (or was dismissed by reflex) meant a 60-to-90-second wait staring at one static sentence. Third, and worst, **a second click was swallowed**: `if (loginInFlight) return;` — a silent no-op, which to the operator is a dead button, and is the single most common way a "stalled" login is actually *experienced*. Harness output, verbatim: `SECOND CLICK PRODUCED STATUSES: 0`, `IN FLIGHT: true`, `HAS cancelLogin EXPORT: undefined`. **What shipped.** A pure stage model (`src/login-stages.js`) that owns per-stage deadlines *and* the failure→recovery mapping, so no failure path can reach the screen without naming something the operator can do; per-stage budgets of 12s/60s/12s chosen against what each stage actually waits on (a machine, a human, a machine — the signer's 90s cut to 60s because beyond a minute the honest conclusion is that the popup never appeared); a cancellable, generation-guarded attempt in `src/auth.js` where a late-settling extension can no longer write status or store a token for an attempt that was abandoned; an absolute `LOGIN_DEADLINE_MS` watchdog as the never-wedge guarantee, because the in-flight latch must not be only as reliable as a browser extension; a busy status that always answers a second click, offering Cancel during the one human-scale stage; and ONE shared status renderer (`src/components/login-status.js`) used by both the login card and the sidebar — they previously had separate implementations and the sidebar's rendered plain text only, so the same failure gave install links on one surface and a dead sentence on the other. 38 new tests (22 pure model, 16 JSDOM integration driving the real flow through the real renderer).

- **CONT-AUTH-1 — sliding sessions + explicit auth state machine. DONE v0.2.92-alpha (agent + frontend + docs + tests; NOT deployed from the subagent — parent hands the operator the deploy block).** **Why.** A session was one fixed window and nothing renewed it: `agent/core/auth.mjs` minted an HMAC token with a hard `exp` at `iat + session_ttl_sec` and there was no refresh path anywhere in the repo. Authorisation was a boolean recomputed per call (`tokenLooksLive`), so there was no state for *about to stop being valid* — the operator's first warning that their session had ended was a bounce to the login page with unsaved work still on screen, mid-keystroke. Raising the TTL was not a fix: a longer fixed window just moves the cliff and weakens the bound on a leaked token. **Done.** (1) Token gains a fourth payload field `oiat` — the moment the owner actually signed — placed **after** the pubkey so index [2] stays the pubkey and the existing browser contract holds; `exp` is now `min(iat + session_ttl_sec, oiat + session_max_lifetime_sec)` so a token can never outlive its own session. (2) New `auth.refreshSession(token)` verifies the presented token, refuses at `oiat + session_max_lifetime_sec` with the terminal code `max_lifetime_reached`, and otherwise re-mints **carrying `oiat` forward untouched** — renewal slides the window but can never move the session's origin, so the cap is unmovable. (3) New `POST /api/auth/refresh` (rate-limited like `/api/auth/verify`, deliberately **not** behind `requireAdmin` — the bearer token is the very claim under examination, and `requireAdmin` would collapse every distinct refusal into one generic 401). Refusals are `expired` / `invalid_session` / `max_lifetime_reached`, none retryable. (4) New pure `src/session-state.js` — five states `anonymous · active · expiring · refreshing · expired` with an injected clock; `refreshing` **is** authorised, so a renewal in flight never evicts anybody, and a `refresh_failed` that is not `max_lifetime_reached` re-classifies rather than ending the session, so a flaky network changes nothing and retries after `RETRY_BACKOFF_MS` (30s). (5) `src/auth.js` owns the one timer that turns those decisions into side effects — timers, clock and network all injected; renewal happens in the background inside the last `REFRESH_WINDOW_SEC` (300s) with **no signer prompt**; starting the loop is idempotent (three starts leave exactly one timer), `endSession` and `stopSessionRefresh` cancel it, and `rehydrateSession` starts one in every fresh tab so a reload does not silently stop the clock. (6) `session_max_lifetime_sec` added to config (default **604800** = 7 days, floored at `session_ttl_sec`) and documented in `agent/config.example.yaml`. (7) The token shape change is **breaking by design**: a 4-field legacy token carries no origin claim, so no cap can be enforced against it — it is rejected as `malformed`, invalidating in-flight sessions exactly once on upgrade; the owner signs one fresh kind-22242 challenge. **Verification.** Agent `node --test test/` **412 pass / 0 fail** (+21: `test/auth-refresh.test.js`, `test/auth-refresh-route.test.js`); root `npx vitest run` **53 files / 1559 pass** (+39: `src/session-state.test.js`, `src/session-refresh-loop.test.js`); every new test is sleep-free. Branch `feature/v0.2.92-alpha-auth-refresh`, annotated tag `v0.2.92-alpha`. **Not deployed.**
