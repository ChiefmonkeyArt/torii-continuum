# Continuum

An app builder, project engine and marketplace for bot work — a gateway into the Torii ecosystem.

Continuum treats every project like a nostr identity: portable, signable, yours. Projects, sessions, milestones, todos, and files are all shaped as nostr events (addressable kinds 30078–30082). MVP stores them in `localStorage`; the same objects flip to signed relay events without re-shaping.

## What's here (v0.2.48-alpha)

**Frontend (`src/`)**

- **Application-first root** at `#/` — logged out, root renders a dedicated branded Amber **login page** in place (NIP-07 / Plebeian Signer, no password auth, no secrets in the DOM); logged in (valid `continuum.session.v1`, or a safely-adopted onboarding session), root routes straight to `#/dashboard`. Routing/auth decisions live in the pure `src/nav-guard.js`; `#/dashboard` is guarded and expired/invalid sessions return to login without a loop.
- **About / Discover** at `#/about` — the marketing surface (sovereignty story, torii-arch hero, promises grid, freedom-tech pillars, live status roadmap) now isolated behind an explicit route, reachable from small non-primary links on the login page. Never the app root or an onboarding completion target.
- **Projects** — list, create, open. Import from GitHub or ngit. Cascades to sessions/milestones/todos/files.
- **Project home** — milestones ladder, session log, live todo list, files created. A per-project **Overview · Board** view switcher lives in the header.
- **Kanban board** — every project ships a board (default columns **Todo · Doing · Done**) at `#/projects/:slug/board`. Add/rename/reorder/delete custom columns (deleting a non-empty column forces a card move — cards are never lost), create/edit/delete cards (title, description, optional assignee + due date), and move cards by drag **or** accessible arrow controls for keyboard/touch. State is per-project, persisted, and Nostr-shaped (kinds 30083/30084).
- **Kanban source sync (read-only)** — boards can surface records imported by the agent from configured local Markdown todo files and public GitHub issues. Imported cards carry a source badge and external link, are never draggable and never mutate local cards, and repeated refreshes never duplicate them (stable per-source fingerprints). A sync bar exposes source/status filters, a manual refresh, and honest last-sync / partial / error / empty / loading states. Imports live only in ephemeral per-board state — never persisted to localStorage or written back to Markdown/GitHub.
- **Marketplace** — open AI-work tasks. Yours highlighted amber.
- **Routstr** — real Cashu wallet top-up when an agent is configured; mock behaviour on demo builds. Default coding model: DeepSeek-Coder-V2. Default chat model: DeepSeek Chat.
- **Dashboard** — cross-project oversight rundown. The Provider card surfaces an admin-gated **wallet health** row (disabled / reachable / degraded / unreachable, with sanitized reasons) alongside model reachability.
- **AI chat dock** — routes through your agent (POST /api/chat) when signed in; falls back to mock replies otherwise.
- **NIP-07 login** — sidebar button opens a Plebeian Signer flow, signs a kind 22242 challenge, and stores the returned session token locally.

**Agent (`agent/`, Node 22 LTS >= 22.4.0 + Fastify)**

A small daemon designed for one operator, one VPS, one npub. Owns:

- NIP-07 login verification (no nsec ever touches the VPS)
- Cashu wallet float on disk (`memory/wallet/`, mode 0600)
- Routstr chat calls (OpenAI-compat, DeepSeek-Chat by default, DeepSeek-Coder-V2 for coding, configurable fallback ladder, one Cashu token per request)
- Read-only **project-source adapters** (`core/project-sources.mjs` + `lib/markdown-todo.mjs`) that normalize configured local Markdown todo files and public GitHub issues into deduped, fingerprinted records. Strict configured allowlists for local paths and GitHub repos; traversal and symlink escapes are rejected; file size, response size, issue/page counts, redirects and timeouts are all bounded; no GitHub credential is used for public repos; content, tokens and full sensitive identifiers are never logged. Last valid snapshots are cached and retained across partial/offline failures.
- Non-mutating **wallet health** check (`GET /api/wallet/health`, admin-gated) that validates mint identity and balance via read-only cashu-ts v3 primitives without touching proofs or wallet state

See `agent/README.md` for the VPS bring-up runbook and `agent/PRIVACY.md` for the invariants.

- Sovereign AI ✅ Constitution `genesis-1.2.0` (digest `03f3e5b6…`) — the first humanitarian article now reads **"Care for the human that created it"**, and two rules join Layer A. `no-credential-custody` is a **safety-floor invariant**: never use a human's password without fresh explicit confirmation *for that specific use*; never store, save, retain, log, reproduce, expose or take custody of passwords, Bitcoin private keys or seed phrases, Nostr private keys or nsec values, or equivalent secrets; reach a genuinely-needed credential through a **secure external reference** so the bot never sees it; **consent to use is not consent to retain**; and **fail closed** where fresh confirmation or secure handling is unavailable. `pareto-focus` is the first **operating rule** — kept in its own array because a priority heuristic is not a sovereignty guarantee — directing the bot to the ~20% of actions producing ~80% of the useful outcome *and to say what it is leaving aside*, with efficiency never overriding safety, consent, privacy, correctness or any duty above it. Already-activated bots are **not** silently rebound: adopting the new covenant is an explicit owner act, the version a bot was born under is never rewritten, and adoption is recorded beside it with an append-only history, so both stay verifiable. The single exception is the safety floor, which binds immediately everywhere — a rule that can only ever cause a *refusal* would otherwise leave existing bots permitted to retain a secret while they waited for a click (v0.2.101-alpha, CONT-COVENANT-1)

- Reliability ✅ Routstr→Ollama fallback on any retryable upstream failure — 5xx, a non-JSON HTML edge error page (including under a 200 status), a wall-clock timeout on the completion request, an empty stream, or a payment/network fault. Every provider failure is a structured `{ code, reason, retryable }` whose reason is classified and sanitised, never a forwarded upstream body, and a malformed request deliberately does **not** fall back (no silent paid→free downgrade masking a bug). The chat dock no longer serves canned mock replies in a build with an agent configured — a failed turn reports an honest, code-keyed error (v0.2.90-alpha, CONT-FALLBACK-1)
- Reliability ✅ One end-to-end wall-clock budget per chat turn. Providers run sequentially, so their independent timeouts used to add up — 45s of Routstr plus 180s of Ollama is 225s under an nginx `proxy_read_timeout` of 120s, so the operator got a 504 or an endless spinner while the agent kept generating into a dead socket. The router now opens a single turn budget (`model_router.total_budget_ms`, default 100s) and clamps every provider call to what remains of it; a fallback with too little time left is not started at all and reports a non-retryable `budget_exhausted` instead, checked **before** any Cashu payment so a doomed turn costs zero sats. The browser fetch is bounded too, at 115s — deliberately between the agent's budget and nginx, so a slow-but-honest reply still lands while a wedged connection surfaces as the SPA's own `client_timeout` rather than a raw proxy 504 (v0.2.91-alpha, CONT-TIMEOUT-1)
- Auth ✅ The sign-in that stayed on the login page was never a routing bug. Two releases rebuilt the navigation machinery and production reported the same sentence back both times — plus a new one after the refresh that finally named the culprit: **"This screen failed to load / Your session is still valid. Reloading usually clears this. / Route /"**. That is the router's fail-closed panel, and the frame it names is the *root* route, because the deployed entry URL `/continuum/` carries no fragment. The throw underneath it came from `src/auth.js`. `setTimeout` on a real `Window` is a WebIDL operation that brand-checks its receiver, and the timer was stored as a property and called as `deps.setTimer(...)` — which passes the wrong receiver and raises `TypeError: Illegal invocation` in every browser, while Node's timers, which ignore the receiver entirely, ran it happily. That one difference is why 1779 tests passed against an app nobody could sign into. Arming token renewal is reached from exactly two places, and they are precisely the two reported symptoms: on the sign-in path it sits one line *before* the session-change dispatch, so the throw skipped it and the transition never began; and inside `rehydrateSession()`, which runs in every route handler, so a reload turned it into the error panel. The natives are now wrapped rather than referenced, so the receiver is the global as WebIDL requires, and arming renewal can no longer take the shell down with it — a session that stops auto-renewing still works until it expires, whereas a screen that will not render is the operator's whole experience. `src/effects/sats-burst.js` carried the identical defect and is fixed with it. Proven by 15 tests that are the first in this repo to install **brand-checked timers as the globals the application actually binds** — every earlier harness inherited Node's permissive ones, which is exactly the gap that let this survive three releases — including one test asserting the harness still rejects the old broken shape, so the fixture cannot quietly loosen later (v0.2.100-alpha, CONT-NAVSYNC-3)
- Auth ✅ The post-auth transition no longer depends on the browser publishing the URL. The previous release moved the render into the same turn as the URL write, which removed the app's reliance on the asynchronous `hashchange` **event** — and production reported the identical symptom afterwards, because the render's *input* had not moved: the router still asked `window.location.hash` **what** to render, and the URL is the one piece of state in this transition the app writes but does not own. A `location.replace()` fragment navigation goes through the browser's session-history traversal queue, so the read-back is not guaranteed to reflect the write in the same turn, and the write can be deferred, silently refused, or throw outright. A stale read made the router render the route for the *old* hash — the login card the operator had just signed in from — and, the guard chain now being synchronous, re-enter itself until the redirect ceiling produced a fail-closed error panel; a blocked write ate the whole transition and left the login card standing with "Signed in." beneath it. The destination is now an **argument, not an observation**: navigation renders the path it was asked for, so the transition is independent of whether the URL write is visible, synchronous, permitted, or announced. The URL write became bookkeeping — best-effort and wrapped, with a fallback from `replace()` to a plain hash assignment — because a stale address bar is cosmetic and a screen that never changes is not. Proven by 29 integration tests that boot the real app at the deployed base path with **no initial fragment** (what an operator typing the address actually has) across four browsers — a URL write that is published, deferred, refused, or throwing — each of which must reach the Dashboard in the turn the signer was approved in with every login surface gone from the document, and every auth and stale-response protection re-asserted under the hostile ones (v0.2.99-alpha, CONT-NAVSYNC-2)
- Auth ✅ A confirmed sign-in opens the Dashboard, in the turn it completed in. The previous release taught the app to refuse a session it could not read back — and once it *could* read one back, the operator still sat on the login card. Signer approved, agent verified, token stored and confirmed, address bar reading `#/dashboard`, login card the only thing on screen; Ctrl+R then opened the Dashboard, which is the proof that storage was correct all along and it was the in-memory transition that never happened. Navigating was writing the URL and hoping: rendering the new route was the sole job of the browser's `hashchange` event, so between the URL write and the event being delivered there was a window in which URL and screen disagreed — and for a browser that coalesces, defers or (for a `location.replace()` fragment navigation) withholds that event, the window never closed. Navigation now *performs* the transition rather than scheduling it: the route resolves in the same turn as the URL write, and the trailing event dedupes against what is already rendered instead of rebuilding it under the operator. A second, quieter copy of the same fault is gone too — the session-change listener re-rendered the sidebar **before** navigating, and an exception inside a listener never reaches the code that dispatched it, so any throw there silently ate the transition; navigation is now first, which on sign-out is the difference between a login card and a dashboard left standing with a dead session. The login attempt is also retired before the session is published, so the Dashboard is never built against a login module that still believes it is mid-attempt and still holds an armed timeout. Every v0.2.97 protection is unchanged and still proven: a tokenless 200, a token born expired, and a cancelled attempt whose reply lands late all navigate nowhere (v0.2.98-alpha, CONT-NAVSYNC-1)
- Auth ✅ A 200 from the agent is not a session, and the app no longer says it is. The previous release bounded every stage and named every signer fault, and sign-in still could not finish: the agent logged `auth.verify.success`, the operator sat on "Verifying your signature… step 3 of 3", then landed back on a login card with no message on it. A tokenless 200 ran the whole success path — session marker written, "Signed in." said, session-change dispatched — after which the nav guard correctly answered that nobody was signed in and the operator was sent back to a login card whose re-render had just rebuilt the status element empty. Completion is now confirmed by reading the state back (a token that stored, parsed, and has not expired) before anything is announced, and each way it can be missing names a different component to fix: a proxy stripping the response body, a body that is not JSON, a token in a shape the client does not read (refused loudly rather than guessed at), a session born expired from clock skew, or a browser that will not keep it because site data is blocked — the last of which is not the agent's fault at all, and used to send those operators to debug a healthy VPS. A born-expired token no longer triggers a sign-out from inside the sign-in, and the terminal status is emitted before the side effects that re-render the surface it is written to, since the router re-resolves even on an unchanged hash. Verified end to end through the real login view, router and guard, because the fault only ever existed at that join (v0.2.97-alpha, CONT-COMPLETE-1)
- Auth ✅ Sign-in works with the NIP-07 signers that actually exist, and blames the right component when it cannot. NIP-07 pins the call, not the answer, so extensions disagree about how much of the event they return — some echo it whole, several NIP-46 bridges return only `{ id, sig }`, some omit `pubkey`, some rewrite `created_at`, and some are injected after the page bundle has run. The flow was written against one of those shapes and forwarded the signer's answer verbatim, so the others reached the agent malformed and came back as "your agent rejected the signature", pointing a working setup at a healthy VPS. The signer's answer is now reconciled against the event it was asked to sign — the signer winning wherever it expressed an opinion, `pubkey` taken from `getPublicKey()`, gaps filled and nothing else touched, which cannot manufacture an acceptance because the agent rehashes and re-verifies independently. A signer that altered the login request is named as the culprit before a round trip is spent on it, a late-injected signer is waited for instead of declared missing, refusals carry a machine-readable code so a key that is not the owner is no longer offered a retry loop that can never succeed, and the install advice lists several signers rather than one (v0.2.96-alpha, CONT-SIGNER-1)
- Auth ✅ A sign-in that did not succeed persists nothing, and the public login screen survives a hard refresh. It used to be possible to cancel a login (or sign out) while the request was on the wire and have the reply store a live token behind the login screen — invisible until the next reload, which then opened the Dashboard from a sign-in that never happened. Auth writes now carry an epoch captured when their request started; sign-out and any abandoned attempt invalidate it, and a superseded reply is reported rather than stored. The guard lives in the module that owns the storage, because the previous release's guard sat one layer above the write and could not stop it. The background renewal stops when the session ends instead of retrying, and boot reads session state through the same authority the route guards use, so the rendered screen and the next refresh cannot disagree (v0.2.95-alpha, CONT-SESSION-1)
- Auth ✅ Sign-in is a bounded, cancellable, three-stage sequence. It used to be an opaque await chain in which only the signer step had a deadline (90s) while the two network steps inherited the generic 30s client budget, there was no way to cancel, and a second click during an in-flight attempt returned silently — so a stalled login presented as one static sentence beside a dead button. Each stage is now bounded against what it actually waits on (challenge 12s, signer 60s, verify 12s), progress shows as "step 2 of 3", a long signer wait escalates its copy instead of looking hung, and every failure names a recovery the UI renders as something pressable — Cancel, Try again, or signer install links. An absolute attempt deadline releases the in-flight latch whatever happens inside, and attempts are generation-guarded so an extension that answers after a cancel cannot resurrect the flow or store a token. Both login surfaces render through one shared status component (v0.2.94-alpha, CONT-LOGIN-1)
- Auth UI ✅ The sign-in / refresh / sign-out surface is wired in a load-bearing order and fails closed. Three symptoms — a login card that stayed open after a successful sign-in, a blank content panel beside a working menu after a hard refresh, and a "Sign out" button that sometimes invoked the signer — shared one cause: boot started the router before mounting the chat dock, the first (synchronous) resolve rendered a view that wrote into a dock that did not exist, and the escaping exception abandoned the rest of boot, including every session/history/storage listener registered after it. `startRouter()` is now last; the router catches view exceptions and renders a visible error panel instead of an empty pane; the agent's stated session expiry is the single authority the guard, the shell control and the renewal clock all read (the token is opaque, and its shape check is deliberately tolerant); the session button's action is bound to the label the operator can actually see; a session change replaces history in both directions; and sign-out clears owner-scoped client state while leaving your local-first project store alone. Verified by 29 integration tests that boot the real app in a real DOM (v0.2.93-alpha, CONT-AUTHUI-1)
- Auth ✅ Sliding sessions with an explicit state machine. A session used to be one fixed window that stopped mid-keystroke, and the operator's first warning was a bounce to the login page with their work still on screen — because "logged in?" was a boolean recomputed per call, with no state for *about to stop being valid*. The browser now runs a pure five-state machine (`anonymous · active · expiring · refreshing · expired`) and renews in the background via `POST /api/auth/refresh` before the token lapses, with no signer prompt. `refreshing` is deliberately still authorised, so a renewal in flight never evicts anybody, and a renewal that fails on a flaky network changes nothing and retries. Renewal cannot extend the session's origin: every token carries `oiat`, the moment the owner actually signed, and a refresh copies it forward untouched — so `session_max_lifetime_sec` (default 7 days) is an unmovable ceiling that no refresh can slide, after which the agent answers a terminal `max_lifetime_reached` and the owner signs a fresh kind-22242 challenge. Upgrading invalidates in-flight sessions exactly once (v0.2.92-alpha, CONT-AUTH-1)
- Ops ✅ Unattended VPS upgrades now default to a CI-built, checksum-verified **release artifact** (production `dist/` + agent source + agent production-only `node_modules`) downloaded from the tag's GitHub Release, instead of cloning the repo and running two `npm ci`s plus a `vite build` on the VPS itself — the dominant cost of the previous 20-35 minute unattended-upgrade path on the resource-constrained chiefmonkey server. `ops/lib/build-release-artifact.sh` builds and CI-publishes a tarball + `.sha256` + manifest (tag/version/commit/subtree hashes) on every tag push, fails closed if any native `*.node` addon or secret-shaped path is found in the staged tree, and enforces tag/version alignment. The VPS-side wrapper (`ops/deploy-unattended.sh`) and the `continuum` Ansible role verify checksum + manifest tag/version + required contents + no-secrets (`ops/lib/artifact-verify.sh`) before extracting straight into the existing atomic staging directory — no `npm ci`, no `vite build` on the VPS in the default path. A non-default agent mount path is detected and automatically routed to the fully-preserved source-build fallback rather than served a mismatched artifact; every other failure mode (missing release, checksum/tag/manifest mismatch) fails closed by default with an explicit opt-in escape hatch. Everything downstream of staging — atomic promote, health/version gate, rollback/rescue, disk retention, systemd/nginx registration, `config.yaml`/encrypted-state preservation — is unchanged. Existing installations transition automatically, no manual migration step. Honest VPS-derated estimate (not yet measured on real hardware, since deployment was explicitly out of scope for this slice): roughly 1-2.5 minutes end to end, plausibly up to ~3-4 minutes pessimistic — inside or near the 2-3 minute target. +72 new tests across 3 files; see `ops/README.md` and `ops/artifact-fast-path-timing.md` (v0.2.103-alpha, OPS-ARTIFACT-1)
